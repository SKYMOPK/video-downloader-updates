# 《Video Downloader》Windows 高質感影音下載器
## Codex 完整開發方案 v2.1

> 本文件是可直接交付開發代理執行的完整需求。相較 v2.0，補強品質與相容性的取捨、早期封裝驗證、任務恢復、依賴更新、測試證據及驗收門檻，並整併重複要求。
> 本文件描述預期成果，不代表其中功能已經實作或通過測試。開發代理收到明確開發指令後，依第十四節開始執行。

### 一、專案定位與核心目標

請擔任本專案的資深桌面軟體工程師、系統架構師、UI/UX 設計師與品質測試工程師，從零開發可直接使用的 Windows 影音下載器，暫定名稱為 **Video Downloader**。

目標環境：

- Windows 10 / Windows 11，64 位元桌面環境。
- 完整繁體中文介面。
- 本機執行，不需要自行架設伺服器。
- 個人偶爾使用，不需要會員、廣告、雲端同步或複雜授權管理。
- 正式使用者不需要安裝 Python、Rust、Node.js 或設定開發環境。

核心流程：

**打開 App → 貼上網址 → 選擇規格 → 開始下載。**

即使幾個月才使用一次，也應能迅速理解操作。介面品質、下載可靠性與部署完整性同等重要。

必要成果包含：

1. 精緻、流暢且一致的現代桌面介面。
2. 盡可能支援一般公開、可正常存取、未受 DRM 保護的 YouTube 影片。
3. 真實的來源格式、畫質、音質與輸出選項。
4. 穩定的下載、合併、轉換、取消、重試與任務恢復。
5. 可維護的下載核心與安全、可回復的更新流程。
6. 可重現的 Windows 建置，以及實際驗證的安裝與使用流程。

不要求保證所有 YouTube 影片永遠成功，不開發 DRM 破解、身分驗證繞過或其他存取限制規避功能。

### 二、範圍與決策優先順序

#### 2.1 核心範圍

正式核心版本包含單部影片解析、影片及音訊下載、真實規格選擇、下載佇列、取消與重試、合併與必要轉換、設定保存、未完成任務恢復、核心版本檢查與更新、Windows 封裝。

以下為穩定後的可選擴充，不得阻礙核心版本交付：

- 播放清單與批次勾選下載。
- 字幕下載與 SRT 輸出。
- 可搜尋的長期下載歷史。
- 更多影音平台。
- 淺色主題；核心版本先完成一致的深色主題。

保存未完成任務是可靠性要求，不等於必須開發完整歷史紀錄頁面。

#### 2.2 需求衝突時的優先順序

依序優先考量：

1. 使用者資料與既有檔案安全。
2. 結果正確、狀態真實、錯誤可恢復。
3. 核心操作直覺、介面完整。
4. 播放相容性與合理來源品質。
5. 處理時間與資源消耗。
6. 額外功能與裝飾效果。

不得為追求最高畫質而未告知使用者就執行耗時重新編碼，也不得為求成功率而偷偷降低使用者明確指定的畫質。

#### 2.3 預設下載策略

一般模式提供兩個清楚的品質策略：

- **建議品質**：在不重新編碼的前提下，優先選擇播放相容性較佳的影音組合；清楚顯示實際解析度、FPS 與輸出容器。
- **最高來源品質**：優先保留來源最佳可用影音品質；必要時使用能容納該組編碼的容器，並提示播放需求。

預設使用「建議品質」。進階選單仍須提供來源真實可用的其他畫質、FPS 與編碼。

任何實際策略都必須以解析到的來源為準，不得假設所有影片都有相同串流。若找不到符合預設相容性目標的組合，顯示可用替代方案，不可悄悄轉碼或謊稱來源品質。

「最高來源品質」不代表升頻、補幀或提升來源本身品質。

優先考慮 UI/UX、設計系統、桌面開發、測試、除錯、程式碼審查與 Windows 部署相關技能。這些是能力類型，不代表環境一定具有同名技能。

### 四、技術架構與早期部署驗證

#### 4.1 必須比較的方案

至少比較：

- **PySide6 + QML**：Python 核心搭配 Qt Quick 介面。
- **Tauri 2 + React + TypeScript**：前端介面搭配本機後端及必要 sidecar。

可以提出其他更合適的方案，但需說明理由。不要僅因某個框架容易產生程式碼就選用。

比較項目：

- 視覺設計能力、鍵盤操作、DPI、Windows 視窗整合。
- UI 回應、啟動速度、閒置資源消耗。
- 含所有依賴的安裝包大小、安裝後大小與首次安裝需求。
- yt-dlp、FFmpeg、FFprobe、EJS 與 JavaScript runtime 的整合及更新方式。
- 程序隔離、取消、崩潰處理與測試可行性。
- 可用 Skills、實際工具鏈、開發與維護成本。
- 封裝、執行環境、最低 Windows 版本及第三方散布要求。

不要把網路上的通用效能數字當成本產品實測。尚未量測時標為假設，建立最小垂直流程後補上結果。

#### 4.2 架構邊界

合理分開：

- UI 與呈現模型。
- 網址驗證與影片解析。
- 格式整理與下載計畫。
- 下載及後處理引擎。
- 任務佇列與狀態機。
- 設定與未完成任務保存。
- 檔案、暫存與輸出驗證。
- 依賴診斷與更新管理。

選擇 Python API 或獨立 yt-dlp 程序都可以，但需說明隔離、更新及程序取消的取捨。不要額外建立沒有必要的常駐本機 HTTP 伺服器。

核心資料模型至少包含來源影片、來源串流、輸出設定、已確認的下載計畫、任務狀態、進度事件、分類錯誤與依賴版本。

每個任務保存獨立、不可被後續 UI 切換修改的設定快照。跨程序或跨執行緒事件需帶任務識別與執行輪次，避免舊事件污染重試後的狀態。

#### 4.3 提早完成封裝驗證

在大量開發前，建立可安裝的最小垂直流程並確認：

1. 安裝後可從一般使用者帳戶啟動介面。
2. 能找到隨附或受控部署的下載、合併與 JavaScript 元件。
3. 能解析一個有權下載的公開來源。
4. 完成一次分離影音下載與合併，驗證輸出檔。
5. 取消時能終止整個相關程序樹。
6. 啟動時不依賴開發目錄、全域 PATH 或開發用工具。

這項工作用於排除部署風險，不取代後續完整介面與正式安裝驗收。若無乾淨 Windows 測試環境，先驗證可取得的環境並記錄缺口。

### 五、UI/UX 與設計系統

#### 5.1 視覺方向

採現代、高質感的深色桌面介面：

- 深灰黑或深藍黑背景，中性深色內容區。
- 克制的藍色或藍紫色重點色。
- 清楚的文字層級、留白、邊框與適量圓角。
- 統一的 SVG 圖示，不以 emoji 代替正式操作圖示。
- 動畫以短暫回饋為主，通常為 150～250ms，尊重降低動畫偏好。
- 避免持續發光、過量卡片、整頁模糊及無意義的裝飾。

集中管理 Colors、Typography、Spacing、Radius、Shadow、Animation Duration 與 Component States。不要直接複製既有產品。

#### 5.2 主畫面

以單一主要工作頁為主，設定使用適合桌面的獨立視窗、側面板或對話框。

主要區域：

1. **頂部列**：App 圖示與名稱、目前任務數、設定、Windows 視窗控制。
2. **網址區**：輸入框、貼上、解析、Enter 操作、網址檢查與解析狀態。
3. **影片資訊**：縮圖、標題、頻道、長度，可取得時顯示日期及一般影片／Shorts 類型。
4. **下載模式**：影片／僅音訊，具有清楚的選取與鍵盤焦點狀態。
5. **輸出設定**：一般模式精簡，編碼等資訊可收合。
6. **下載控制**：儲存位置、處理方式摘要、開始下載。
7. **任務區**：來源、檔名、階段、進度、速度、剩餘時間及適用操作。

開始按鈕附近需以一般使用者能理解的方式顯示，例如「1080p・60 FPS・MP4・需合併影音」。若會重新編碼，明確標示「需要轉換，可能花費較長時間」。

縮圖維持來源合理比例；長標題支援省略及查看完整內容；無來源、無任務、載入中與錯誤都應有完整設計。

#### 5.3 互動規則

- 貼上後可自動解析，也提供手動解析；使用去重與取消機制避免重複工作。
- 新網址開始解析後，舊結果不得回寫覆蓋新結果。
- 剪貼簿只在使用者觸發貼上或明確啟用對應功能時讀取，不持續監控。
- 影片連結附帶播放清單參數時，核心版本只處理該影片並給予清楚提示。
- 尚未成功解析、選項不成立或儲存位置不可用時，開始按鈕不可啟動任務，並顯示原因。
- 任務完成後可開啟檔案或資料夾；不要自動播放下載內容。
- 自訂標題列仍需保留拖曳、最大化、還原、縮放與常用 Windows 操作。
- 重要錯誤保留到使用者能處理，不以短暫消失的訊息作為唯一說明。

#### 5.4 尺寸、鍵盤與可及性

階段 0 定義並記錄最小視窗尺寸。建議由約 900 × 640 邏輯像素起評估，依實測調整，不以固定尺寸掩蓋溢出。

驗證 100%、125%、150% DPI，並兼顧常見較小工作區；放不下時內容可合理捲動，重要操作仍可取得。

支援合理的 Tab 順序、清楚焦點、Enter 解析、對話框 Esc，以及可辨識的圖示按鈕名稱。不只用顏色區分狀態。動畫、進度更新不得反覆搶走焦點。

#### 5.5 必須實際檢查的畫面

首次啟動、空狀態、解析中、解析成功、影片模式、音訊模式、下載中、合併／轉換中、完成、失敗、取消、待恢復任務、依賴異常與設定畫面。

另檢查長標題、繁體中文、特殊字元、小視窗與 DPI。透過測試注入重現罕見狀態時，證據必須註明是測試情境；正式功能不可依賴假資料。

### 六、YouTube 解析與真實格式

#### 6.1 下載核心

優先使用 yt-dlp、FFmpeg、FFprobe，以及目前官方建議的 EJS 與 JavaScript runtime 配置。依實作當下官方文件確認版本及散布方式，不重新發明解析引擎。

公開不代表一定可以不登入存取。年齡、地區、登入或其他限制需清楚分類；不得保證無憑證可下載所有公開影片。

第一版不加入登入憑證或瀏覽器 cookies 匯入。若未來需要，作為另外的需求與隱私設計處理。

直播中、尚未首播的來源應識別並清楚提示；已結束且可作一般影片存取的直播回放，依實際解析結果處理。

#### 6.2 真實來源資訊

取得來源實際提供的串流，合理呈現解析度、FPS、編碼、容器、是否含音訊與大小資訊。

- 沒有 4K 就不能顯示為原生 4K 可下載。
- 同解析度不同 FPS、編碼或容器應合理區分。
- 將影片解析度與音訊串流分開建模，再產生可執行的影音組合。
- 估計檔案大小需標明「估計」；資訊不足時顯示未知，不虛構。
- 若來源有多音軌，顯示實際選用音軌；有語言資訊時明確標示，避免選錯語言。
- Shorts 類型以可取得的可靠資訊判斷，不只依影片長度猜測。

解析結果不等於永久有效的下載憑證。任務等待過久或重試時可重新解析，但需保留原本選擇條件並再次驗證。

### 七、影片、音訊與輸出正確性

#### 7.1 影片

支援 MP4、MKV、WebM，依來源與編碼相容性提供可行選項。

清楚區分：

- 直接下載。
- 影音合併。
- 無損重新封裝。
- 重新編碼轉換。

容器與編碼是不同概念。不能僅改副檔名假裝轉換，也不能把所有來源任意封裝成任何容器。

預設避免重新編碼；需要轉碼時先顯示處理方式及影響，由使用者在已知情況下開始任務。不支援的組合停用並解釋原因。

#### 7.2 音訊

提供：原始最佳可用音訊、MP3、M4A、Opus、WAV。

清楚區分「來源品質」與「輸出設定」。有意義且可實際產生時提供 128、192、256、320 kbps 等選項，不為所有格式硬套同一位元率清單。

- 原始模式盡量保留來源音訊，不進行無意義轉碼。
- WAV 顯示合適的 PCM 設定與較大檔案提醒，不套用 MP3 式音質階級。
- 來源約 128 kbps 轉成 320 kbps，不代表來源音質提升。
- M4A 選項需明確對應實際音訊編碼與處理方式。
- 一般使用者可直接選「最佳來源音質」，不用理解全部參數。

#### 7.3 輸出完成條件

任務只有在以下條件成立後才能標記完成：

1. 下載程序及必要後處理成功結束。
2. 預期最終檔案存在且非空。
3. FFprobe 可辨識預期串流與容器，影片／音訊模式符合任務設定。
4. 最終檔已安全落在使用者選定位置，並記錄實際路徑。

日常完成檢查不必完整解碼整部長影片；正式測試另外執行片段解碼與播放檢查。驗證失敗不得顯示成功。

### 八、任務狀態、取消與恢復

#### 8.1 任務狀態機

至少區分：等待中、解析中、下載中、合併中、轉換中、驗證中、已完成、失敗、取消中、已取消、待恢復。

制定可允許的狀態轉移；完成、失敗與取消事件不得互相覆蓋。取消與完成同時發生時，以已確認的實際檔案及程序結果判定，保留完整成果並如實呈現。

分別處理來源串流下載進度與後處理階段。音訊與影片分開下載時，不得把兩次 0～100% 誤顯示為整體完成後又倒退。

可取得總位元組時，合理彙整下載階段；資訊不足就顯示目前子階段或不定進度。合併、轉換及驗證沒有可靠百分比時使用不定進度，不虛構總進度。

UI 進度事件需節流、批次更新或採等效方式，避免高頻輸出拖慢介面。

#### 8.2 佇列與重試

- 多任務佇列，預設同時下載數為 1，設定提供保守上限。
- 下載與轉碼分別考量資源限制，避免多個轉碼同時耗盡 CPU。
- 自動重試僅用於可恢復的暫時性錯誤，採有限次數、退避與適量隨機延遲。
- 明確存取限制、空間不足、無效設定不無限重試。
- 不同層級的重試需有總預算，避免應用程式與核心各自重試而倍增等待。
- 明確指定的格式消失時，提供真實替代選項，不偷偷換成較低規格。

#### 8.3 取消與關閉

取消必須涵蓋解析、下載、JavaScript runtime、FFmpeg 與所有相關子程序。先嘗試正常停止，逾時後以受控方式終止程序樹，驗證沒有孤兒程序。

核心版本採用以下關閉行為：

- 沒有執行中任務時直接關閉。
- 有執行中任務時，提供「繼續下載」與「停止任務並結束」。
- 核心版本關閉後不繼續在背景下載，不預設增加系統匣常駐。
- 結束前保存任務資料，停止程序並保留可用中間檔。

#### 8.4 重啟與續傳

設定與必要任務資料採適合本機的可靠保存方式；可使用 SQLite 或原子替換的結構化檔案，不需要資料庫伺服器。

程式意外結束或電腦重開後：

1. 未完成任務標為「待恢復」，不得直接假設仍在下載。
2. 顯示可恢復任務，由使用者選擇重試或移除。
3. 重新解析取得有效來源，再判斷中間檔能否續傳。
4. 無法續傳時說明並重新下載，不保證每個來源都可接續。

不要把易過期的媒體 URL 當作唯一恢復依據。合併完成但最終搬移失敗時，保留可驗證成果並提供重新儲存，避免強迫重新下載。

### 九、錯誤處理與檔案安全

#### 9.1 錯誤分類

至少包含：網址無效、影片不存在、無法存取、來源受限制、格式不可用、解析核心異常、網路中斷、逾時、寫入失敗、空間不足、合併／轉換失敗、依賴缺失或不相容。

錯誤辨識可能不完全可靠。無法確定原因時顯示「目前無法完成」及可行操作，保留診斷資訊，不把所有未知錯誤硬判成核心過時。

使用者看到簡潔繁體中文說明及重試、改格式、換目錄或檢查更新等適用操作。技術記錄可另行查看或複製，但不能只呈現原始堆疊。

#### 9.2 路徑與檔名

- 預設下載目錄、自訂位置、記住上次位置與開啟資料夾。
- 支援繁體中文、Unicode、保留名稱、尾端空白／句點及非法字元處理。
- 依完整路徑長度處理檔名，截斷時保留識別與副檔名。
- 預設以安全編號處理同名衝突，不覆蓋既有檔案。
- 並行任務對輸出名稱的保留需避免競爭，不能只在開始時檢查一次。
- 外接磁碟移除、目錄權限變更與網路磁碟失效時保留可恢復資料。

#### 9.3 暫存管理

每個任務使用可追蹤的工作區，優先考量最終儲存磁碟的空間及安全落檔方式。跨磁碟搬移需處理額外空間需求與失敗恢復。

- 成功後清理本任務可安全移除的中間檔。
- 取消、失敗或待恢復任務保留可續用資料；預設保留 7 天，提供清理入口並顯示占用。
- 到期清理只作用於 App 管理且可確認歸屬的暫存，不刪除使用者下載成品。
- 有可靠大小資訊時預估所需空間，並預留合併／轉換空間；大小未知不代表磁碟一定足夠。
- 執行中仍需處理空間耗盡，不依賴開始前的一次檢查。

#### 9.4 安全與隱私

- 網址驗證支援合理的 YouTube 官方網址形式，避免過窄規則拒絕一般連結。
- 子程序使用參數陣列，不拼接 shell 命令；使用者輸入不能成為額外命令參數。
- 使用受控依賴路徑，避免意外載入目前工作目錄中的同名工具。
- 不意外沿用使用者全域 yt-dlp 設定、外部插件或任意執行指令。
- 不收集遙測，不上傳紀錄，不儲存敏感憑證。
- 本機記錄輪替並限制容量；診斷匯出移除權杖、敏感查詢參數及不必要的個人路徑資訊。
- 說明解析、下載與更新會連線來源平台或官方元件服務，不把「本機執行」誤述為完全離線。

產品說明簡短提醒依適用法律、授權與平台規則使用即可，不增加每次下載的法律彈窗或版權檢查系統。

### 十、設定與元件更新

#### 10.1 設定

保持精簡：預設目錄、模式、品質策略、同時下載數、完成通知、核心及依賴版本、更新檢查與暫存清理。

提供立即可用的預設值。設定損毀時使用安全預設並保留可診斷資訊，不因單一設定檔異常而無法啟動。

#### 10.2 依賴組合

記錄 App、yt-dlp、EJS、JavaScript runtime、FFmpeg／FFprobe 的實際版本、取得來源、相容性與建置資訊。EJS 是否已隨所選發行形式提供，依官方文件確認，不重複下載或假設一定存在。

不必讓全部元件一起更新，但每次啟用新版本，都必須驗證所需的相容組合。

#### 10.3 更新流程

不需要自行建立更新伺服器，但正式核心版本須提供可實際完成的受控核心更新流程：

1. 檢查官方或明確受信任來源的版本資訊。
2. 顯示目前及目標版本、必要依賴變更，由使用者確認。
3. 下載至獨立暫存位置，設定逾時與合理大小限制。
4. 驗證來源及完整性；官方提供可驗證簽章時使用適當的信任根。不可把任意同源雜湊描述為完整的來源真偽保證。
5. 在啟用前執行版本與必要能力檢查。
6. 執行中任務繼續使用原版本，不覆寫使用中的工具。
7. 安全切換版本，保留可回復版本；啟用失敗時回復，App 仍可啟動。

官方服務不可用、檔案驗證失敗、更新取消或空間不足時，不損壞現有版本。更新 App 本體可先採重新安裝新版的簡單流程，不必為此建立完整自動更新服務。

### 十一、Windows 正式交付

提供：完整原始碼、固定或可追溯依賴版本、可重現建置與測試命令、正式圖示、64 位元執行程式、合適安裝包、繁體中文使用說明及第三方授權資訊。

安裝原則：

- 優先一般使用者範圍安裝，避免無必要的系統管理員權限。
- 處理 WebView2、Qt 或所選方案的必要執行環境，不假設開發機已安裝就等於使用者環境具備。
- 明確列出實際支援並測試的 Windows 版本與組建。
- 不要求使用者自行設定 PATH 或執行套件管理器。
- 升級保留設定與必要任務資料，對資料格式變更做受控遷移。
- 解除安裝不刪除使用者下載成品；移除偏好或 App 管理資料需明確處理。
- 程式碼簽署狀態與實際可取得的發行條件如實記錄，不承諾沒有測試過的系統信任體驗。

確認所選元件及實際散布版本的授權要求，包含必要聲明或其他義務；不要只列專案名稱而忽略具體套件組成。

若無法產生或測試某種 Windows 產物，提供可重現腳本並清楚標示缺口，不能把腳本存在視為安裝包已驗收。

### 十二、測試與品質證據

#### 12.1 固定、可重現的測試

使用授權清楚的本地素材、固定格式資料及可控制失敗的測試替身，驗證：

- 格式整理、輸出計畫、容器與編碼相容性。
- 任務狀態轉移、事件順序、取消／完成競爭與重試。
- 多串流進度、未知大小與後處理狀態。
- 設定保存、損毀恢復、任務重啟與資料遷移。
- 中文及特殊檔名、長路徑、同名競爭。
- 網路錯誤、磁碟不足、權限錯誤與輸出驗證失敗。
- 更新取消、驗證失敗、相容性失敗與回復。

除單元測試外，使用實際打包的核心及 FFmpeg 做整合測試。模擬通過不代表線上下載或正式安裝已通過。

#### 12.2 YouTube 線上相容性測試

目標至少 20 個不同、授權依據可記錄的來源，涵蓋短片、長片、Shorts、720p／1080p／1440p／4K、30／60 FPS、不同影音編碼、分離串流及格式缺失。

優先使用自有測試素材或明確允許下載與測試的來源，記錄權利人授權、授權頁面或其他可確認依據。不得僅因影片公開就推定有下載授權。

可用同一來源涵蓋多種格式，但不要把 20 個操作組合誤報為 20 個不同來源。另設無效、不存在、受限制等負向案例，不混入正常來源成功率。

分層控制成本：

- 所有正常樣本測試完整解析與格式辨識。
- 代表性組合測試下載、合併、音訊輸出與播放。
- 長片可用片段測試編解碼，但至少保留一個完整長影片下載案例。
- 報告清楚區分完整下載、片段驗證及僅解析，不能互相代替。

每次記錄測試日期、App 與核心版本、Windows 環境、來源識別、授權依據、請求規格、實際串流及輸出、結果、失敗原因與重試次數。

分別統計解析成功率、下載成功率與輸出有效率，標明各自分子、分母、排除原因及首次成功／重試後成功，不以單一百分比掩蓋問題。

如果環境或授權素材不足，保留缺口，不用無授權素材補數字，也不宣稱完整相容性驗收。

#### 12.3 輸出有效性

測試不只看程序回傳碼，還需檢查容器、影音串流、解析度、FPS、音訊編碼、時長及預期音軌。對代表性樣本執行解碼檢查與實際播放，確認影音同步及無明顯破損。

檢查時考量可變幀率、音訊編碼延遲及來源本身資訊誤差，不以僵硬的單一相等判斷誤報。

#### 12.4 UI、資源與生命週期

實際啟動打包版，確認 UI 不凍結、鍵盤可操作、DPI 正常、動畫自然、沒有溢出、取消無殘留程序。

階段 0 記錄量測方法與初始預算；最小封裝流程完成後以實測確認或調整，附理由：

- 冷啟動到可操作時間。
- 閒置 CPU 與包含子程序的記憶體占用。
- 解析／下載／合併中的回應情況。
- 安裝包與安裝後實際大小，區分共享及額外安裝的執行環境。
- 重複解析、下載、取消及恢復後的程序、記憶體與暫存變化。

不得反覆調高預算掩蓋回歸。與基準相比出現持續性退化時，先調查原因。沒有工作時避免無必要輪詢與持續動畫。

執行多輪完整流程及至少一個長任務，驗證關閉、重啟、斷網恢復與失敗重試。進度密集時視窗仍可拖動及操作，取消操作立即提供可見回饋。

#### 階段 0：環境、決策與部署風險

完成環境與 Skills 盤點、官方文件確認、框架比較、架構決策、設計 Tokens、資料模型、測試策略、資源量測預算與最小封裝垂直流程。

#### 階段 1：完整單片流程與精緻 UI

完成主畫面、空狀態、解析、影片資訊、模式切換、真實規格、儲存位置、單片下載、合併、基本轉換、可靠狀態與基本錯誤處理。

通過條件：實際打包程式可完成影片及音訊流程；核心輸出選項能正確執行；完成狀態經輸出驗證；主要畫面、DPI 與鍵盤操作已檢查。不能以靜態展示取代功能，也不能留下明顯粗糙的 UI 等待不確定的未來美化。

#### 階段 2：可靠性與日常使用

完成佇列、取消程序樹、有限重試、續傳判斷、未完成任務保存、重啟恢復、通知、檔案衝突、暫存管理、設定、依賴診斷與安全核心更新。

完善正式圖示、安裝包、依賴、建置腳本、版本資訊、說明及第三方授權；完成乾淨 Windows 環境的安裝、啟動、下載、升級與解除安裝驗證。

通過條件：符合第十四節驗收要求，交付證據及未驗證清單。無法取得的測試環境如實列出，不擅自宣稱全數通過。

#### 階段 4：可選擴充

僅在核心版本穩定後，再評估播放清單、字幕、歷史及其他來源，不為增加功能數量降低既有品質。

#### 每階段報告

簡要列出完成內容、實際 Skills、關鍵決策、測試及結果、修正事項、缺口與下一步。以證據為主，避免重複宣示品質。

### 十四、最終驗收與執行要求

#### 14.1 必須達成

- 正式介面可操作、繁體中文完整、視覺一致，指定尺寸與 DPI 下沒有阻斷操作的排版問題。

- 不虛構來源品質、進度或完成狀態，不在未告知下改變明確規格。
- 取消釋放程序，單一失敗不當機，關閉及重啟行為符合規格。

- 提供完整原始碼、可重現建置、實際產物、依賴資訊及使用說明。
- 明確區分已驗證、部分驗證與未驗證；重大缺口不得隱藏在完成宣告中。

#### 14.2 交付前 Quality Review

依「製作 → 測試 → 評估 → 改善 → 再測試」迭代。

找出最粗糙的畫面、最容易誤解的操作、最脆弱的錯誤流程，以及最影響維護的結構問題，直接修正後重新驗證。不可只回報明顯可修的問題就停止。

不因第一次執行成功就宣布完成；也不要求與變更無關的重複測試。測試應對準實際風險，已通過且沒有新變更的檢查不無限重跑。

#### 14.3 現在開始開發時的指令

收到執行本方案的明確要求後，立即從階段 0 開始，接續完成階段 1～3。
